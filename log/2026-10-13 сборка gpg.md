# Сборка gpg

Дата: 2026-10-13. Утилита — авторский разбор OpenPGP в `Security`: пакеты, ASCII-armor, проверка подписи RSA. Библиотека `libr3` берётся из соседнего дерева `R3-lib`. SHA-1, SHA-512 и MD5 лежат в `src/` этого репозитория.

Каталоги рядом:

```
/home/{name}/Security
/home/{name}/R3-lib
/home/{name}/godminer
```

В Makefile это `R3=../R3-lib`. Каталог godminer для сборки не нужен.

## Как собрать

Сначала статическая библиотека R3 под ту же архитектуру, что и утилита. На этой машине это x86_64:

```sh
make -C ../R3-lib
```

Получается `../R3-lib/libr3_x86_64.a`. В неё уже входит SHA-256 (на x86_64 — SHA-NI). Карантин `r3_stream` / `r3_core_strncpy` в эту библиотеку не входит.

Затем утилита:

```sh
cd Security
make            # gpg и cksum
make clean      # удаляет ./gpg, ./cksum и src/r3_args.o
```

Ключи те же, что в `godminer/src/netd_minimal.mak`:

```
-march=native -ffast-math -ftree-vectorize
-std=gnu11 -O3 -fPIC
-D_GNU_SOURCE -U_FORTIFY_SOURCE -fno-stack-protector -D_BITS_STDIO_H
-DGnuPG
-s -pthread
```

Плюс `-lm -lz` и `-Wl,-u,sha256`, чтобы из архива вытянулся объект SHA-256 вместе с его конструктором регистрации. Без `-u` линкер архив по конструктору не подхватывает.

На armv7 и aarch64 Makefile подставляет те же `-march`, что godminer (`armv7-a`+NEON либо `armv8-a+crypto`). Библиотеку R3 надо собрать с тем же `ARCH`.

Проверка подписи RSA SHA-256 (нужен системный `/usr/bin/gpg` только чтобы выписать ключ и отсоединённую подпись во временный каталог):

```sh
test/test_gpg_rsa.sh
```

Ожидаемая последняя строка: `rsa sha256: key ok, file ok, tamper rejected`.

Запуск разбора:

```sh
./gpg --help
./gpg --import pub.pgp doc.sig          # бинарные пакеты
./gpg --armor message.asc               # снять Radix-64 и проверить CRC-24
```

Ключ читается `--import` до файла подписи. Для отсоединённой подписи документ ищется рядом: у `doc.sig` снимается суффикс `.sig`.

## Что делает утилита

Собираются `src/gpg_sign.c`, `src/gpg_armor.c`, `src/sign.c`, `src/rsa.c`, `src/gzip.c` и хеши ниже. Точка входа — `main` под `-DGnuPG`.

Разбор бинарных пакетов старого формата (бит 0x80) и нового (бит 0xC0):

- открытый и секретный ключ, User ID, подключ;
- подпись v3 (печать полей) и v4 (хеш и проверка RSA);
- one-pass;
- литерал (байты документа для подписи);
- ZIP внутри пакета сжатия (`gzip.c`, zlib).

ASCII-armor (`--armor`): найти блок `-----BEGIN PGP ...-----`, снять Base64, сверить CRC-24 OpenPGP. Кодирование в armor утилита не делает.

Проверка RSA (алгоритмы OpenPGP 1 и 3) в `pgp_signature_verify` / `rsa_EME_pkcs_verify`:

1. хеш подписанных данных;
2. старшие 16 бит хеша против двух октетов в пакете подписи;
3. возведение подписи в степень `e` по модулю `n`;
4. сравнение хвоста блока PKCS#1 с самим хешем.

Текст результата: `Сертификация пройдена!` или `Сертификация НЕ пройдена!`. Код выхода при отказе остаётся 0.

Что именно хешируется:

- тип 0x00 — бинарный документ (из литерала или из файла без `.sig`);
- типы 0x10…0x13 — сертификация User ID: пакет ключа и User ID;
- типы 0x18 и 0x19 — привязка подключа.

DSA, ECDSA и EdDSA: из пакета читаются R и S, криптопроверки нет. Подпись утилита не создаёт.

Если `digest_select` не нашёл хеш, печатается `hash alg N не собран в этой утилите` и процесс не падает. Раньше здесь был пустой указатель: длина хеша читалась до проверки.

## Хеши в этой сборке

Проверено отдельным прогоном `digest_select` после линковки.

| id | имя | источник |
|---:|---|---|
| 1 | MD-5 | `src/md5.c` |
| 2 | SHA-1 | `src/sha1.c` |
| 4 | SHA-256 NI | `libr3`, объект вытянут `-Wl,-u,sha256` |
| 5 | SHA-384 | `src/sha512.c` |
| 6 | SHA-512 | тот же файл |
| 7 | SHA-512/224 | тот же файл |
| 8 | SHA-512/256 | тот же файл |
| 9 | SHA3-224 | `src/shake256.c` |
| 10 | SHA3-256 | тот же файл |
| 11 | SHA3-384 | тот же файл |
| 12 | SHA3-512 | тот же файл |
| 13 | GOST R 34.11-94 CryptoPro | `src/gosthash.c` |
| 14 | GOST R 34.11-94 Test | тот же файл |
| 15 | STRIBOG-256 | `src/stribog.c` |
| 16 | STRIBOG-512 | тот же файл |
| 17 | Blake2s | `src/blake2s.c`, копия из R3-lib |
| 18 | Blake2b | `src/blake2b.c`, копия из R3-lib |

Нет отдельного SHA-224 (SHA-2). SHA-512/224 — другое усечение и в таблице уже есть. OpenPGP-алгоритм 10 — SHA-2-512, его даёт `src/sha512.c`. Это не SHA3-512 и не Streebog-512. SM3 в `src/sm3.c` есть, регистрация закрыта `#if 0`, в `hmac.h` нет `MD_SM3`, в сборку не входит.

`src/blake2b.c` и `src/blake2s.c` — обычные копии файлов из R3-lib, не симлинки. Файл для компилятора лежит в `Security/src`, и `#include "hmac.h"` берёт заголовок Security, а не соседний заголовок R3. Номера id у этих заголовков после SHA3 расходятся (в R3 между ними стоят SHAKE и SM3). Если компилировать `blake2b.c` прямо из каталога R3, BLAKE2 регистрируется под чужим номером и `digest_select(MD_BLAKE2B)` из утилиты его не видит.

В `src/hmac.h` у `MDigest` добавлено поле `digest`: инициализаторы SHA3 в `shake256.c` его задают. Смещение прежних полей не менялось.

## Правки, без которых сборка на GCC 14 не сходится

- `src/gpg_build.h`. `_aligned_malloc` в `libr3` — это `mmap`. `free` по такому адресу роняет процесс в `rsa_public_key_free` уже после проверки. В сборке утилиты оба имени — `memalign` / `free`.
- `src/rsa.h`. В репозитории заголовка не было, `rsa.c` подхватывал чужой прототип из R3 и не компилировался. Локальный заголовок совпадает с определениями в `src/rsa.c`. Опечатка `hash_tag_sha3_356` исправлена на `hash_tag_sha3_256`.
- `src/segment.h`. Его требует `src/sign.h`. Файл тот же, что в godminer: атрибут секции регистрации.
- `src/stribog.c`, `src/gosthash.c`. Четвёртый аргумент `_addcarry_u64` приведён к `unsigned long long *`. GCC 14 считает `uint64_t *` другим типом.
- `src/gosthash.c`. Конструктор `gost94_init_` больше не печатает `Init paramset` на каждый запуск.
- `godminer/test/sha1.c`, это не дерево Security. Перед локальной функцией `htole32` стоит `#undef htole32`. С `-D_GNU_SOURCE` это имя уже макрос из `<endian.h>`, и функция не компилировалась.

## Проверка 2026-10-13

`test/test_gpg_rsa.sh` на ключе RSA 2048 и хеше SHA-256:

- самоподпись ключа (тип 0x13): `Сертификация пройдена!`, старшие октеты хеша `ok`;
- отсоединённая подпись файла `payload-for-rsa`: `Сертификация пройдена!`;
- тот же файл с дописанным байтом `X`: подпись документа `Сертификация НЕ пройдена!`, самоподпись ключа по-прежнему принята.

Первый прогон без SHA-256 в ключе GnuPG падал: сертификация ключа была SHA-512, объекта SHA-2-512 тогда не было, чтение `md->hash_len` шло по пустому указателю. Теперь SHA-2-512 собран. Тест по-прежнему ставит `cert-digest-algo SHA256`.

## MD5

Пометка «не работает» из `src/md5.c` снята: на векторах RFC 1321 она не подтвердилась. Прогон того же файла: пустая строка, `a`, `abc`, `message digest`, алфавит, буквы с цифрами, 80 цифр. Все семь сумм совпали с RFC. Длины 0, 1, 55, 56, 63, 64, 65, 127, 128 и 129 байт совпали с OpenSSL и при подаче по одному байту, и кусками по 13 байт. Расхождений нет.

## cksum

`make cksum` собирает утилиту по списку `src/Makefile-cksum`: `cksum.c`, `crc16_clmul.c`, `r3_args.c`, заголовок `src/crc.h`. Демонстрационный `main` в `r3_args.c` компилируется как `r3_args_demo`, точкой входа остаётся `cksum.c`. На Linux `<intrin.h>` заменён на `<x86intrin.h>`, для PCLMUL добавлен `-flax-vector-conversions`. Для файла из байтов `abc` сумма совпала с GNU `cksum`: `1219131554 3`.

`src/crc.h` и `src/ecc.h` переведены из CP1251 в UTF-8.

## Что не класть в коммит

- `./gpg` и `./cksum` — продукты `make`;
- `src/r3_args.o`;
- объекты и `libr3_*.a` / `libr3_*.so` соседнего R3-lib.
